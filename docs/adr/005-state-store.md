# ADR-005. Хранилище состояния: SQLite через SQLAlchemy

Статус: принято. Дата решения: 2 сентября 2026, при реализации хранилища. Дата записи: 3 сентября 2026.

## Контекст

Очередь предложений, журнал и счётчики лимитера общие для всех аналитиков и обязаны переживать перезапуск сервиса. Проект живёт на одном сервере с 7,6 ГБ памяти, где уже стоят Oracle и шесть контейнеров трассировки.

## Решение

SQLite, доступ через SQLAlchemy ORM.

SQLite потому, что запись идёт одним процессом, объёмы маленькие, а лишняя база данных на этом сервере стоит памяти, которой нет. SQLAlchemy потому, что переход на PostgreSQL при появлении второго рабочего процесса должен быть строкой подключения, а не переписыванием слоя доступа.

Состояние лимитера лежит там же, а не в памяти процесса: лимит, который снимается ожиданием развёртывания, не лимит.

## Альтернативы

**Модуль sqlite3 напрямую.** Отклонено: на переходе к PostgreSQL пришлось бы переписывать каждый запрос, а условие перехода известно заранее.

**PostgreSQL сразу.** Отклонено по замеру памяти: свободно около 2,3 ГБ, и они нужны эталонным прогонам.

**Состояние в памяти процесса.** Отклонено: перезапуск теряет чужое подтверждение и обнуляет квоты.

## Последствия

Хорошее: ноль дополнительных контейнеров, схема описана типами, миграция сводится к строке подключения.

Плохое: один пишущий процесс. Условие, при котором это перестаёт работать, записано в `docs/not-done.md`.

Запись задним числом: решение принято и реализовано 2 сентября, ADR записан 3 сентября, когда обнаружилась висящая ссылка из `SPEC.md`. Содержание решения не менялось, изменился только момент записи, и это здесь названо.
