# ADR-011. Эталонный набор живёт в git, а не в хранилище состояния

Статус: принято. Дата: 3 сентября 2026.

## Контекст

`SPEC.md`, раздел 4, перечисляет содержимое хранилища состояния: очередь предложений, журнал, счётчики лимитера, эталонный набор. Первые три там уместны: это состояние, общее для аналитиков, оно меняется в работе и переживает перезапуск.

С эталонным набором иначе. Главное его свойство названо в разделе 8 спеки: вопросы и эталонный SQL пишутся и коммитятся до того, как автор трогает промпт агента. Доказательством служит история git.

Набор в SQLite это свойство не выдерживает. У базы нет истории, нет ревью, нет диффа. Утверждение «набор написан раньше промпта» превращается в слово автора, а именно этого слова здесь и не хватает: набор пишет автор проверяемой системы.

## Решение

Отклонение от `SPEC.md`, раздел 4. Эталонный набор хранится в git как файлы: один вопрос, один YAML в `evals/dataset/`, замороженные ответы эталонных запросов в `evals/expected/`.

В хранилище состояния остаётся то, что действительно состояние: очередь, журнал, лимитер. Позже туда добавятся результаты прогонов, если появится панель с историей прогонов; сами вопросы туда не переезжают.

Подтверждённые пары «вопрос, SQL» от аналитика (`SPEC.md`, раздел 3, шаг 10) попадают в очередь на добавление в набор, но в набор входят через коммит, а не автоматически. Иначе набор растёт тем, что агент уже умеет, и точность растёт сама собой.

## Альтернативы

**Хранить в SQLite, как написано в спеке.** Отклонено: теряется доказательство порядка работ, теряется ревью вопроса, теряется дифф при изменении эталонного числа.

**Хранить в обоих местах, файлы как источник, база как кэш.** Отклонено: две копии расходятся, и вопрос «какая из них считалась» возникает ровно в момент разбора неудачного прогона.

## Последствия

Хорошее: порядок работ проверяется командой `git log`. Изменение эталонного числа видно как дифф и требует объяснения в сообщении коммита. Десять вопросов заказчика добавляются файлами, без миграций.

Плохое: панель не может показать набор запросом к своей базе, ей придётся читать файлы. Для тридцати вопросов это не проблема; на тысяче была бы.

Правится: `SPEC.md`, раздел 4, строка про содержимое хранилища состояния.
