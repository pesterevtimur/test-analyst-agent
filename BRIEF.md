## 4. Основной сценарий

Действующие лица: бизнес-пользователь, аналитик, агент.

1. Бизнес присылает вопрос обычным языком. Пример: «Продажи по регионам за второй квартал 2001 по каналам, с долей промо».
2. Аналитик передаёт вопрос агенту через панель или чат.
3. Агент через MCP: находит нужные таблицы по семантическому слою, собирает SQL, прогоняет через ограничители, предлагает аналитику на подтверждение (SQL, план, ожидаемый объём).
4. Аналитик подтверждает, правит или отклоняет. Решение записывается.
5. Агент выполняет запрос (только чтение, лимиты), проверяет результат на правдоподобие, формирует ответ: таблица, короткое пояснение, как получен, ограничения интерпретации.
6. Аналитик отправляет ответ бизнесу. Подтверждённая пара «вопрос, SQL» попадает в эталонный набор.
7. Всё видно в трассах и панели: шаги, инструменты, время, стоимость.

Расширение (описать, не делать): бизнес пишет агенту напрямую, режим ограничен предодобренными типами вопросов.

## 5. Архитектура по слоям

Слой данных. Oracle Database Free 23ai в Docker (образ gvenzl/oracle-free, slim-вариант), схема SH ставится скриптом инициализации из db-sample-schemas. Отдельный пользователь AGENT_RO с SELECT на SH. Если успеем: профиль БД с лимитом CPU и времени сессии.

Слой MCP-сервера. Python 3.12, официальный MCP SDK, python-oracledb в thin-режиме, sqlglot, pydantic. Инструменты:
- describe_schema(table?): описание таблиц и полей из семантического слоя (YAML на русском: смысл таблицы, смысл полей, ключи, связи, типовые фильтры, известные ловушки). Это ядро ценности: для SAP такой слой переводит MATNR и EBELN в бизнес-термины.
- propose_query(question, sql): разбор sqlglot в диалекте Oracle, только SELECT, allowlist таблиц и колонок, обязательный лимит строк, оценка через EXPLAIN PLAN. Возвращает id предложения и вердикт ограничителей.
- execute_query(proposal_id): выполняется только для подтверждённого предложения. Политика: авто для простых запросов (до N строк, не более K таблиц), иначе требуется подтверждение аналитика. Таймаут, лимит строк, результат плюс метаданные.
- sanity_check(result_id): проверки правдоподобия (пустой результат, число строк, сходимость агрегатов при наличии итогов).
Журнал: каждый вызов пишется в трассу Langfuse и в локальную таблицу истории. Транспорт: по документации OpenClaw (stdio или HTTP), выбрать тот, что проще подключить.

Слой агента. OpenClaw с одним агентом «аналитик данных», системная инструкция с процессом из раздела 4, подключённый MCP-сервер, набор инструментов ограничен четырьмя выше. Никаких других инструментов у агента нет: ни shell, ни файлов, ни веба.

Слой проверки. Раздел 6.

Слой наблюдаемости и управления.
- Langfuse self-hosted (compose с официального репозитория): трассы, наборы данных, эксперименты, судья.
- Панель управления, минимум: FastAPI плюс HTMX. Очередь предложений на подтверждение, история запусков со ссылками на трассы, переключатели инструментов и политики подтверждения, кнопка остановки текущей задачи. То, что панель OpenClaw даёт из коробки, не дублировать.

Слой документов. Раздел 8.

## 6. Автоматическая проверка (решение принято до старта)

Принято: слои. Обязательные: 1, 2, 7. Минимальные: 5, 6. Процессный: 8. Перспектива: 3 частично, 4.

1. Ограничители до выполнения, в MCP-сервере: разбор SQL, только SELECT, allowlist, лимит, таймаут, read-only пользователь БД. Детерминированно, стоимость ноль.
2. Эталонный набор и проверка по результату: 20-30 вопросов на SH на русском с эталонным SQL. Сравнение результатов выполнения, не текста SQL. Режим мягкий, как в Spider 2.0: ответ верен, если содержит все ключевые значения эталона; порядок строк и лишние колонки не считаются ошибкой; для чисел допуск. pytest, запуск локально и в CI GitHub Actions при каждом изменении. Метрики: точность по результату, доля отказов ограничителей, среднее число шагов.
3. Проверки правдоподобия после выполнения: минимум в sanity_check.
4. Самопроверка агента с голосованием: не делаем, в ADR как отклонённое.
5. LLM-судья: один судья в Langfuse для текста пояснений (обосновано ли пояснение данными результата, нет ли выдумок). Не блокирует, только оценка.
6. Оценка траектории: у каждого эталонного вопроса ожидаемые инструменты и максимум шагов, проверяется по трассе в тех же тестах.
7. Трассировка: каждый прогон в Langfuse, ссылка из панели.
8. Аналитик как источник разметки: подтверждённые пары «вопрос, SQL» дописываются в эталонный набор автоматически.

## 7. Ограничения и доступы агента (docs/limits.md)
