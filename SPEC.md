# SPEC: агент-аналитик над данными Oracle и SAP

Версия 1, 2 сентября 2026. Источник истины по содержанию работы. Собран из `BRIEF.md` и разбора с Тимуром 2 сентября.

Правило изменения: любое отклонение от этого документа сначала оформляется как ADR в `docs/adr/`, потом реализуется. Правило работы: `CLAUDE.md`.

## 1. Что делаем и зачем

Агент, который ускоряет работу аналитика над вопросами бизнеса к данным Oracle и SAP. Аналитик остаётся владельцем ответа, агент снимает с него механическую часть: поиск таблиц, сборку запроса, проверку результата, оформление.

Проблема, из которой всё выросло: очередь запросов к команде аналитики расписана на два года вперёд. Часть вопросов бизнеса просто не доходит до ответа.

Что считаем успехом:
- пять сценарных вопросов проходят полный путь с подтверждением аналитика;
- на эталонном наборе есть измеренная точность по результату, отдельно на запечатанном подмножестве;
- видно и можно вмешаться: шаги, запросы, стоимость, остановка, подтверждение, переключатели;
- посчитана польза в часах и деньгах, с явно названными допущениями;
- документы раздела 14 существуют и не противоречат этому файлу.

## 2. Границы

Входит: слой данных, MCP-сервер, агент, автоматическая проверка, наблюдаемость, панель управления, документы.

Не входит: процесс ABAP-разработки, генерация синтетических данных, голосование по нескольким вариантам SQL, мониторинг живого трафика, аутентификация в панели сложнее одного пароля, развёртывание в контуре заказчика, шина данных (обоснование в `docs/backlog.md`, раздел 3).

Вынесено в `docs/backlog.md` и берётся только после того, как основная часть проходит критерии раздела 14: второй набор данных SFLIGHT, перенос принципа проверки на задачи миграции и конвертации.

Допущения:
- Данных заказчика нет. Берём Oracle Database Free в контейнере и схему SH (Sales History) из `oracle-samples/db-sample-schemas`, около десяти таблиц.
- Поверх SH строим тонкий слой представлений с именами в стиле SAP. Он показывает ту боль, ради которой затевался семантический слой: техническое имя поля не читается человеком.
- Модель: `deepseek-v4-pro` через совместимый с OpenAI интерфейс. Архитектура от поставщика модели не зависит: замена не должна требовать правок в MCP-сервере и проверке.
- Среда выполнения агента: OpenClaw. Запасной вариант OpenCode, если OpenClaw не встанет за половину дня.
- Доступ к данным только на чтение, отдельный пользователь Oracle с правом SELECT на схему SH.
- Аналитика работает на отчётной реплике, а не на транзакционной базе. Учётной записи агента в транзакционной базе не существует, ADR-009.

Проектируем на команду 10-15 аналитиков, реализуем на одном сервере. Швы под масштабирование перечислены в разделе 11.

## 3. Действующие лица и основной сценарий

Бизнес-пользователь задаёт вопрос. Аналитик владеет ответом. Агент ускоряет шаги.

1. Бизнес присылает вопрос обычным языком.
2. Аналитик передаёт вопрос агенту в мессенджере.
3. Агент читает семантический слой через `describe_schema`, собирает SQL и отдаёт его в `propose_query`.
4. `propose_query` прогоняет шесть детерминированных проверок, оценивает объём через EXPLAIN PLAN и кладёт предложение в очередь с вердиктом.
5. Политика решает: простое предложение выполняется сразу, остальные ждут аналитика.
6. Аналитик в панели видит вопрос, SQL, план, оценку объёма и вердикт по каждой проверке. Подтверждает, правит или отклоняет. Решение записывается.
7. `execute_query` выполняет подтверждённое предложение с таймаутом и лимитом строк.
8. `sanity_check` проверяет результат на правдоподобие.
9. Агент возвращает в мессенджер ответ: таблица, короткое пояснение, как получено, чем ограничена интерпретация.
10. Аналитик отправляет ответ бизнесу. Подтверждённая пара «вопрос, SQL» уходит в эталонный набор.

Вопросы и ответы идут в мессенджере, подтверждения в панели. Разведено намеренно: подтверждать SQL в чате с телефона нельзя, нужно видеть план и ожидаемый объём, и всё подтверждённое должно лежать в одном месте для аудита.

Расширение, описываем и не делаем: бизнес пишет агенту напрямую, режим ограничен предодобренными типами вопросов.

## 4. Компоненты

Всё слушает `127.0.0.1`, наружу только через ssh-туннель.

| Компонент | Что это | Решение |
|---|---|---|
| Слой данных | Oracle Database Free в контейнере: транзакционная база `FREEPDB1` и отчётная реплика `REPPDB1` | агент работает только с репликой, учётной записи в транзакционной базе у него нет, ADR-009 |
| MCP-сервер | Python, официальный MCP SDK, `python-oracledb` в тонком режиме, `sqlglot`, `pydantic` | транспорт `streamable-http`, ADR-003 |
| Хранилище состояния | SQLite: очередь предложений, журнал, счётчики лимитера, эталонный набор | доступ через SQLAlchemy, ADR-005 |
| Агент | OpenClaw, один агент «аналитик данных», модель `deepseek-v4-pro` | `toolFilter` ограничивает набор четырьмя инструментами |
| Панель | FastAPI и HTMX | только то, чего нет в панели OpenClaw, раздел 10 |
| Наблюдаемость | Langfuse, самостоятельное размещение | выбран по замеру памяти, ADR-008 |

OpenClaw это самостоятельный шлюз между мессенджерами и агентским циклом, а не библиотека внутри нашего процесса. Отсюда транспорт: при `stdio` OpenClaw порождает процесс на сессию, и общего состояния между аналитиками не получается, а нам нужны общая очередь, общий лимитер и общий журнал.

## 5. Контракты инструментов

Все контракты описаны моделями `pydantic`, на каждый есть тест. Ошибка возвращается как данные, а не как исключение: агент должен прочитать причину и исправиться.

### describe_schema(table?)

Отдаёт семантический слой: таблицы с бизнес-именами, колонки с человеческими названиями, типами и описанием, ключи, разрешённые связи, типовые фильтры, ловушки, объявленные метрики.

Без аргумента отдаёт всё: на десяти таблицах это влезает в контекст, а поиск по словарю нечем оправдать. Условие, при котором поиск понадобится, записывается в `docs/not-done.md`.

Колонки с персональными данными помечены, их значения не выдаются никогда.

### propose_query(question, sql)

Шесть проверок по порядку, все детерминированные, без участия модели:

1. Разбор `sqlglot` в диалекте Oracle. Ровно одна инструкция, только SELECT. Ни DML, ни DDL, ни PL/SQL, ни второй инструкции через точку с запятой.
2. Все таблицы и колонки внутри allowlist. Allowlist собирается из семантического слоя, руками не пишется.
3. Персональные колонки не запрашиваются.
4. Лимит строк обязателен. Если его нет, он дописывается.
5. Соединения только из объявленных связей.
6. EXPLAIN PLAN, оттуда оценка стоимости и ожидаемого числа строк.

Возвращает: идентификатор предложения, нормализованный SQL, вердикт по каждой из шести проверок отдельной строкой, оценку объёма, решение политики (автовыполнение либо ожидание подтверждения) с причиной.

Вердикт списком, а не одним словом. Отказ без причины бесполезен и аналитику, и агенту.

### execute_query(proposal_id)

Принимает только идентификатор, никогда не принимает SQL. Это главный инвариант конструкции: приём текста запроса обходил бы все шесть проверок одним вызовом.

Выполняет только предложение в статусе «подтверждено» или «автовыполнение». Таймаут и лимит строк задаются на уровне сессии базы, а не надеждой на вежливость запроса. Маскирование применяется к результату повторно, на выходе.

Возвращает: идентификатор результата, строки, число строк, время, признак усечения.

### sanity_check(result_id)

Проверки правдоподобия: пустой результат; число строк ровно равно лимиту, значит ответ усечён; агрегат целиком из null; отрицательные суммы там, где их быть не может; расхождение разбивки с итогом, если запрошено и то и другое.

Возвращает список наблюдений с уровнем и человеческим объяснением.

### Инварианты

- Предложение одноразовое. Повторное выполнение невозможно, иначе подтверждение обходится повтором.
- Предложение привязано к пользователю. Подтвердить чужое нельзя.
- Каждый вызов пишется в журнал и трассу до и после, включая отказы.

## 6. Семантический слой

Ядро ценности. Гибрид словаря и объявленных метрик.

Словарная часть: смысл таблицы, смысл каждого поля, ключи, связи, типовые фильтры, ловушки. Ловушки пишутся свободным текстом по-русски: это знание аналитика, которое нигде не записано, и формализация его убьёт. Пример настоящей ловушки в SH: квартал в `TIMES.calendar_quarter_desc` хранится строкой вида `2001-02`, а не числом.

Метрическая часть: объявленные сущности, меры и разрешённые соединения. Выручка объявлена один раз и считается одинаково всегда.

Правило использования, жёсткое: если метрика объявлена, агент обязан использовать её и не имеет права считать по-своему. Если метрика не объявлена, агент пишет SQL сам, но обязан пометить ответ строкой «определение не из словаря, проверьте». Пометка показывает аналитику, куда смотреть, и служит заявкой на пополнение словаря. Подтвердил определение, оно уехало в словарь, следующий такой вопрос уже детерминированный.

Устройство:
- Источники описаний это список каталогов, а не один файл. Представления в стиле SAP и потом SFLIGHT подключаются конфигурацией, без правок MCP-сервера и ограничителей.
- Маскирование персональных данных объявляется флагом на колонке в том же файле. Ограничитель читает тот же источник. Один источник правды, а не список в словаре и второй в коде.
- Allowlist таблиц, колонок и соединений строится из семантического слоя автоматически.

## 7. Возможности, ограничения, доступы

Агент может: читать описанную часть схемы, предлагать SQL, выполнять подтверждённые запросы в пределах лимитов, объяснять результат, помечать неуверенность.

Агент не может: писать в базу, видеть что-либо вне allowlist, выполнять запрос без прохождения проверок, обходить подтверждение, вызывать что-либо кроме четырёх инструментов. Ни оболочки, ни файлов, ни веба.

Лимиты в три уровня, потому что счёт запросов защищает от частоты и не защищает от тяжести:

1. Ведро жетонов на пользователя. Стартовые значения: пополнение 1 запрос в минуту, ёмкость ведра 5, суточный потолок 100.
2. Ограничение одновременных выполнений: 2 на пользователя, 6 на всех. Общий потолок важнее пользовательского: сумма пользовательских лимитов заведомо больше того, что вывезет база.
3. Бюджеты на задачу: строки на запрос, время запроса, число шагов, число запросов, бюджет токенов.

Бюджет токенов считается с явным запасом на рассуждение модели. Замер 2 сентября: один вызов с вызовом инструмента дал 471 токен входа и 954 выхода, из них 770 ушло в рассуждение. При бюджете 600 токенов модель израсходовала весь бюджет на размышление и не дошла до вызова инструмента.

Состояние лимитера лежит в SQLite вместе с очередью, а не в памяти процесса. Иначе перезапуск сервиса обнуляет квоты, и обход лимита сводится к ожиданию развёртывания.

Исчерпание лимита это внятный ответ: что кончилось, когда восстановится, что делать. Событие идёт в трассу и видно в панели. Поднятие лимита требует причины текстом, причина уходит в журнал.

Персональные поля `CUSTOMERS` (имя, телефон, почта) маскируются в семантическом слое, в результатах и в трассах.

Журналирование: кто, что, когда, какой SQL, сколько строк, сколько времени, сколько стоило.

## 8. Проверка

Слои проверки и их роль:

| Слой | Роль | Статус |
|---|---|---|
| Ограничители до выполнения | детерминированно, стоимость ноль | обязательный |
| Эталонный набор, сравнение по результату | главный критерий качества | обязательный |
| Трассировка | разбор любого прогона | обязательный |
| Проверки правдоподобия | `sanity_check` | минимальный |
| Судья по тексту пояснения | оценка, не блокирует | минимальный |
| Оценка траектории | ожидаемые инструменты и максимум шагов | минимальный |
| Аналитик как источник разметки | подтверждённые пары дописываются в набор | процессный |
| Сценарии давления | проверка запретов состязательно | обязательный |
| Голосование по вариантам SQL | не делаем | отклонено, ADR-001 |

### Эталонный набор

30 вопросов, разложены по трём осям сразу:
- по классам сложности из раздела 9, чтобы качество и деньги считались на одних вопросах;
- 20 рабочих и 10 запечатанных, запечатанные не открываются до финального прогона;
- 6 вопросов из 30 это ловушки, где правильный ответ отказ: таблица вне allowlist, неоднозначная формулировка, вопрос без ответа в этих данных.

Набор пишет автор агента. Это смещение, и оно названо прямо в `docs/verification.md`. Смягчения: вопросы и эталонный SQL пишутся и коммитятся до того, как автор трогает промпт агента и семантический слой (порядок доказывается историей git); запечатанное подмножество прогоняется один раз; формулировки берутся из бизнес-языка и документации схемы, а не из собственного семантического слоя. Место под десять вопросов от заказчика оставлено: они вставляются в набор без переделок.

### Как сравниваются результаты

По результату выполнения, не по тексту SQL. Режим мягкий с одним ужесточением:
- порядок строк не важен;
- лишние колонки не ошибка;
- числа сверяются с относительным допуском 0.5%;
- лишние строки это ошибка, ADR-007. Лишняя строка означает неверный фильтр, то есть чужие данные в ответе бизнесу. Для отчётности это хуже недобора.

Эталон задаёт ключевые колонки и меры. Совпадение считается по ключу, значения мер сверяются с допуском.

### Проверка соблюдения инструкций

Проверить «все инструкции» целиком нельзя. Каждая инструкция делается проверяемой по отдельности, непроверяемые удаляются.

1. Всё, что можно вынести из промпта в ограничитель, выносится. Ограничитель не зависит ни от модели, ни от формулировки.
2. Оставшееся в промпте нумеруется, на каждый номер минимум один тест. Инструкция без теста удаляется из промпта: она не работает, а только съедает контекст. Метрика: доля инструкций, покрытых тестом.
3. Оценка траектории по трассе: ожидаемые инструменты и максимум шагов.
4. Судья по тексту пояснения, на модели, отличной от той, что писала ответ.
5. Негативные сценарии в наборе, где правильный ответ отказ.
6. Сценарии давления по методике `harness/meta-skills/skill-creator/addenda/pressure-testing.md`: три и более одновременных давления, требование выполнить без подтверждения. Правильное поведение это отказ с объяснением и предложением, что можно сделать вместо. Пока сценарии не пройдены, поведение не считается рабочим.

### Метрики отчёта

Точность по результату двумя строками, на рабочих и на запечатанных (расхождение и есть мера подгонки). На ловушках доля правильных отказов против выдумок. Доля отказов ограничителей и сколько из них по делу. Соответствие траектории. Покрытие инструкций тестами. Шаги, время и стоимость на вопрос по классам сложности.

### Запуск

Два набора с разной ролью, ADR-006:

Первый, на каждый push в CI: контракты, шесть проверок ограничителей, валидация семантического слоя, сборка allowlist, покрытие инструкций тестами. Без модели. Быстро и детерминированно.

Второй, эталонный прогон: требует модели и базы, стоит денег и времени, недетерминированный по природе. Запускается по расписанию и вручную перед сдачей, отчёт с метриками коммитится в `evals/reports/`.

Причина разделения: недетерминированный тест в блокирующем CI приучает команду игнорировать красный билд, и вместе с ним перестают читать настоящие поломки.

## 9. Модель пользы

Две разные величины, они продаются по-разному:

Трудозатраты, часы аналитика на вопрос. Это операционные затраты.
Время ожидания, сколько вопрос лежит в очереди. Это охват отчётности, те самые данные, до которых команда не доходит.

Классы сложности и оценка трудозатрат (источник: оценка Тимура, сентябрь 2026, не замер):

| Класс | Что это | Оценка |
|---|---|---|
| Простой | одна-две таблицы, метрика известная | 0.5-1 час |
| Средний | несколько таблиц, надо разобраться в смысле полей и ловушках | 3-7 часов |
| Сложный | новая область, нужна сверка с источником и разбор расхождений | 1-3 дня |

Арифметика очереди: длина очереди считается из потока запросов в неделю и среднего времени обслуживания по классам. Показывает, откуда берутся два года, и на тех же формулах показывает, что меняется, когда простой класс уходит агенту.

Финансовая модель: экономия часов против стоимости работы агента. Стоимость агента считается из замеренного расхода токенов. Замер 2 сентября: около 0.2 цента за шаг по ценам вне часа пик, около цента за задачу из пяти шагов. На фоне часа аналитика это ноль, поэтому ограничением является не стоимость, а задержка: около 13 секунд на шаг, около минуты на задачу.

Все входные числа помечены источником. Оценка называется оценкой, замер называется замером.

## 10. Наблюдаемость и панель

В трассу на каждый вопрос: сам вопрос, каждый вызов инструмента с входом, выходом и временем, вердикт шести проверок, решение политики, подтверждение аналитика с именем и временем, выполненный SQL, число строк, время в базе, токены и стоимость, итоговый ответ.

Сквозной идентификатор связывает сообщение в мессенджере, вызовы MCP, строку в SQLite и карточку в панели.

Персональные значения в трассу не попадают: маскирование применяется до записи, а не после. Иначе трасса становится второй копией данных, через которую обходятся ограничения доступа.

Локальный журнал в SQLite дублирует ключевое. Трассировка это удобство, журнал это обязанность: замена системы трассировки не должна ломать аудит.

Панель OpenClaw уже даёт сессии, живую страницу задач с отменой запущенного, показ каждого вызова инструмента с входом, результатом, прогрессом, ошибками и подтверждениями, и расход. Это не дублируется.

Наша панель, четыре экрана:

1. Очередь предложений: вопрос, SQL, план, оценка объёма, вердикт по каждой из шести проверок, кнопки подтвердить, поправить, отклонить. Правка создаёт новое предложение, старое остаётся с пометкой: история решений важнее аккуратности списка.
2. История: запуски, статус, время, стоимость, кто подтвердил, ссылка на трассу.
3. Лимиты: квоты по людям, состояние вёдер, переключатели политики, поднятие лимита с обязательной причиной.
4. Эталонный набор: вопросы, последний прогон, метрики, кнопка добавить подтверждённую пару в набор.

Аутентификация: один пароль, как в границах брифа. Полноценной аутентификации нет, подтверждающий выбирается из списка. Это названо прямым текстом в `docs/limits.md` и `docs/not-done.md` вместе с тем, что нужно для промышленной эксплуатации.

## 11. Швы под масштабирование

Проектируем на 10-15 аналитиков, реализуем на одном сервере. Пять мест заложены сразу, чтобы масштабирование было настройкой, а не переписыванием контрактов:

1. Очередь предложений живёт в базе, а не в памяти процесса.
2. Выполнение оформлено как задача с идентификатором и статусом, а не как синхронный вызов. Появятся долгие запросы, включится ожидание без смены контракта.
3. Личность пользователя сквозная с первого дня: кто предложил, кто подтвердил, чей бюджет, чей журнал.
4. Лимиты на пользователя, а не глобальные.
5. Пул соединений к базе и профиль ресурсов на пользователя базы.

Открытый технический вопрос: передаёт ли OpenClaw личность пользователя в вызов MCP. Проверяется на дне 2 при подключении. Запасной вариант, если не передаёт: отдельная конфигурация подключения на аналитика со своим статическим заголовком. Некрасиво, работает на 10-15 людях, записывается в `docs/not-done.md`.

## 12. Решения и открытые вопросы

Принятые решения, каждое становится ADR:

| ADR | Решение |
|---|---|
| 001 | Проверка: сравнение по результату выполнения как главный критерий, ограничители в MCP-сервере, судья только для текста. Отклонено: сравнение SQL по тексту, судья как основной критерий, голосование по вариантам |
| 002 | Среда выполнения: OpenClaw. Зафиксировать находку, что это шлюз мессенджеров со своим агентским циклом, и следствия для панели |
| 003 | Транспорт MCP: `streamable-http`, не `stdio`, ради общего состояния между аналитиками |
| 004 | Модель: `deepseek-v4-pro` вместо облачной модели Anthropic |
| 005 | Хранилище состояния: SQLite вместо отдельной СУБД |
| 006 | CI разделён на быстрый детерминированный набор и отдельный эталонный прогон |
| 007 | Лишние строки в результате считаются ошибкой, вопреки мягкому режиму Spider 2.0 |
| 009 | Аналитика работает на отчётной реплике `REPPDB1`, транзакционная база `FREEPDB1` агенту недоступна. Смоделирована граница доступа и отставание данных, не смоделированы применение журнала и отдельная машина |
| 008 | Система трассировки: Langfuse. Замер показал 1971 МиБ на шесть контейнеров, Phoenix остаётся запасным с записанным условием перехода |

Открытые вопросы к заказчику (ответы могут прийти в процессе, закладывается возможность смены): предметная область данных, формат сдачи, обязателен ли OpenClaw или это был пример.

Открытые вопросы к Тимуру: стоимость часа аналитика с накладными и поток запросов в неделю (нужны для финансовой модели, раздел 9).
