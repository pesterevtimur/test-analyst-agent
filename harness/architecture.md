# Architecture

Этот документ описывает четыре слоя системы, как они взаимодействуют, и какие контракты соблюдаются между ними.

---

## 1. Зачем нужно разделение на слои

Главная проблема «обычной работы с ИИ» в том, что всё перемешано: знания живут в чате, навыки повторяются от сессии к сессии, контекст переписывается заново. Это даёт **lossy compression на каждом шаге**.

Разделение на слои решает три вещи:
1. **Знания компаундируются** (wiki-слой переживает сессии).
2. **Навыки переиспользуются** (skills-слой это портативная компетенция).
3. **Контракты делают агента дисциплинированным** (schema-слой задаёт правила игры).

---

## 2. Четыре слоя

```
┌─────────────────────────────────────────────────────────────────┐
│ Слой 4. SKILLS                                                  │
│   Переиспользуемые рабочие процедуры. Активируются по описанию. │
│   .claude/skills/wiki-ingest/, .claude/skills/code-architecture-helper/, ...    │
└────────────────────────────┬────────────────────────────────────┘
                             │ читает schema, читает wiki, пишет wiki
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│ Слой 3. SCHEMA (CLAUDE.md)                                      │
│   Контракт: «как этим проектом пользоваться». Корневой + один   │
│   на каждую wiki. Это «программа», превращающая агента из       │
│   чатбота в дисциплинированного wiki-мейнтейнера.               │
└────────────────────────────┬────────────────────────────────────┘
                             │ описывает правила для слоёв ниже
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│ Слой 2. WIKI                                                    │
│   LLM-сгенерированные markdown-страницы. Entity, concept,       │
│   sources, contradictions. Каждый факт с citation на raw.       │
│   wikis/<domain>/                                               │
└────────────────────────────┬────────────────────────────────────┘
                             │ ссылается на raw, никогда не пишет в raw
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│ Слой 1. RAW                                                     │
│   Immutable источники: PDF, web-clip, transcript, table.        │
│   Никто не редактирует. Только append.                          │
│   wikis/<domain>/raw/                                           │
└─────────────────────────────────────────────────────────────────┘
```

Дополнительно есть два горизонтальных слоя, не вписывающиеся в эту лесенку:

- **MCP-серверы и tools** это «руки» агента: file ops, web search/fetch, поиск в wiki через qmd, и т.д.
- **`skill-creator`**: мета-слой: единственный канал создания новых skills.

## 3. Контракты между слоями

### Raw → Wiki (только через `wiki-ingest`)

- Raw immutable. Wiki никогда не редактирует raw.
- Каждый файл в raw имеет **stable ID** (slug + edition). Пример: `gost-r-12345-2024.pdf` → ID `gost-r-12345`, edition `2024`.
- При добавлении новой редакции (`gost-r-12345-2026.pdf`) старая остаётся, новая получает edition `2026`. Зависимые wiki-страницы помечаются как **stale**, пока `wiki-ingest` не пересчитает значения.
- Таблицы из raw извлекаются в `data/tables/<slug>.csv` + sidecar `data/tables/<slug>.meta.yaml` с провенансом.

### Wiki → Skills (только через `wiki-query`)

- Skill не читает raw напрямую. Только wiki. Если wiki не покрывает, skill вызывает `wiki-ingest`.
- Это force-функция: пробелы в wiki становятся видимыми, а не закопанными в context window отдельной сессии.

### Skill → Skill

- Skills могут вызывать друг друга, но **только декларативно**: skill A в своём `SKILL.md` пишет «когда X, используй skill B». Никакой динамической диспетчеризации.

### CLAUDE.md → всё

- Корневой `CLAUDE.md` это «оглавление». Что и где лежит. Какие skills доступны.
- Wiki-локальный `CLAUDE.md` это «как ингестить и запрашивать **эту конкретную** wiki». Может задавать тон, требования к detail, специфичные lint-правила.

## 4. Анатомия wiki-страницы

Все wiki-страницы это markdown с YAML frontmatter. Минимальная схема:

```yaml
---
type: entity | concept | source | contradiction | comparison
slug: <уникальный-в-рамках-wiki>
created: 2026-05-12
updated: 2026-05-12
sources: [src:anthropic-skills-2025, src:karpathy-llm-wiki-2026]
status: draft | blessed | stale
edition: 2026.05
---

# <Title>

## Summary
Короткое описание, **обязательно с citation-маркерами** на каждый факт.

## Key facts
- Утверждение X ^[src:anthropic-skills-2025:§intro]
- Число Y = 100 ms ^[src:anthropic-skills-2025:§perf]

## Related
- [[other-entity]]
- [[concept-name]]

## Open questions
...
```

**Citation-маркер**: `^[src:<source-id>:<locator>]`. Локатор это секция, страница, timestamp в видео и так далее.

## 5. Анатомия skill

Соответствует [Anthropic Agent Skills spec](https://agentskills.io/specification):

```
skill-name/
├── SKILL.md                    # обязательно
│   ├── YAML frontmatter
│   └── Markdown инструкции (< 500 строк)
├── references/                 # дополнительные доки, загружаются on-demand
├── scripts/                    # исполняемый код для детерминированных шагов
├── assets/                     # шаблоны, иконки, фикстуры
└── evals/
    └── evals.json              # тест-кейсы
```

Поля frontmatter, набор закрытый:

| Поле | Обязательное | Ограничения |
|---|---|---|
| `name` | да | до 64 символов, строчные латинские буквы, цифры и дефис, совпадает с именем папки |
| `description` | да | до 1024 символов, что делает скилл и когда его применять, «пушинговая» формулировка |
| `license` | нет | имя лицензии или ссылка на файл |
| `compatibility` | нет | до 500 символов, требования к среде |
| `metadata` | нет | произвольные пары строка-строка, только строки |
| `allowed-tools` | нет | список предодобренных инструментов через пробел, экспериментальное |

Своих корневых ключей быть не должно. Всё, что не влезает в `metadata` строкой (происхождение, списки сценариев), пишется в тело скилла разделом `## Provenance`.

Проверить скилл на соответствие спеке:

```bash
skills-ref validate ./skill-name
```

**Прогрессивное раскрытие**: три уровня:
1. Metadata (name + description, ~100 токенов): всегда в контексте.
2. Тело SKILL.md (~3–5k токенов): когда skill активирован.
3. references/scripts: по запросу.

Это то, что позволяет иметь сотни skills без раздувания контекста.

## 6. Lint-контракты (детально)

`wiki-lint` запускается:
- После каждого `wiki-ingest` (auto).
- По запросу `wiki-lint <domain>`.
- В CI, если wiki в git.

Проверки:

| Проверка | Severity | Что значит |
|---|---|---|
| `missing-citation` | **critical** | Фактическое предложение без citation-маркера |
| `broken-citation` | critical | Citation ссылается на несуществующий source-id |
| `orphan-page` | warning | Страница без входящих `[[ссылок]]` |
| `stale-claim` | critical | Source-edition обновился, но страница не пересчитана |
| `unresolved-contradiction` | warning | Есть `contradictions/<...>.md` без поля `resolution` |
| `table-as-prose` | critical | Раздел выглядит как пересказ таблицы (regex: «состоит из», список с числами без таблицы) |
| `flat-index` | warning | `index.md` > N строк без под-индексов |
| `unindexed-page` | warning | Страница не зарегистрирована в `index.md` |

Critical → ingest падает, страница не публикуется. Warning → лог + sticky-todo в `log.md`.

## 7. Как это всё работает в одной сессии

Пример: пользователь говорит «спроектируй мне message-bus для микросервисов на Kafka».

1. **Trigger.** Description у `microservice-design` skill матчит запрос. Claude активирует skill.
2. **Skill читает свой SKILL.md.** Там написано: «прежде чем писать код, сходи в `wikis/microservices/` и `wikis/code-architecture/` через `wiki-query`».
3. **wiki-query.** Идёт grep по `wikis/microservices/`, находит страницы `kafka.md`, `event-sourcing.md`, `message-contracts.md`. Возвращает их содержимое + citation-маркеры.
4. **Decision.** Если в wiki нет покрытия конкретного аспекта, skill вызывает `wiki-ingest` для добавления (пользователь даёт источник или skill ищет в вебе через MCP).
5. **Generation.** Skill пишет код. В комментариях кода ссылки на конкретные wiki-страницы как rationale.
6. **Post-condition.** Если по ходу всплыли новые факты (например, новая версия Kafka API), skill записывает их обратно в wiki через `wiki-ingest` (это «answers flow back», как у Карпатого).

## 8. Чего этой архитектурой не решаем (явно)

- **Multi-user concurrency.** Если двое одновременно ингестят в одну wiki, нужны блокировки. Не решаем, пользователь один.
- **Privacy/permissions per page.** Wiki плоская по правам. Если нужно, заводится отдельный домен.
- **Realtime sync.** Wiki не отвечает на запросы за миллисекунды. Это база знаний, не БД.
- **Очень большой масштаб.** Карпатый говорит про ~100 источников / сотни страниц. Дальше начинает требоваться нормальный поиск (qmd) и, возможно, embedding. Это уже не «light».

## 9. Глоссарий

См. [`glossary.md`](./glossary.md) (создастся позже). Базовые термины здесь:

- **Skill**: папка с `SKILL.md`, описывающая переиспользуемую процедуру. Активируется LLM по description.
- **MCP**: Model Context Protocol; способ подключения внешних систем к агенту. Это «доступ», не «поведение».
- **Tool**: функция, которую агент вызывает (file_write, web_search, и т.д.).
- **Raw**: immutable источник истины (PDF, web-clip, transcript).
- **Wiki**: LLM-генерируемое markdown-представление, читаемое и редактируемое только через skills.
- **Schema / CLAUDE.md**: конфигурационный файл, задающий правила работы агента с проектом или wiki.
- **Citation-маркер**: inline-аннотация `^[src:<id>:<locator>]`, привязывающая факт к raw-источнику.
- **Edition**: версия источника. При обновлении старая остаётся, зависимые wiki-страницы помечаются stale.
- **Ingest**: операция добавления нового источника в wiki.
- **Lint**: проверка инвариантов wiki (citation coverage, orphans, stale claims, etc).
